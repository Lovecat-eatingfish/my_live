> 三种部署形态的完整操作手册。端口总表见 [端口总表.md](端口总表.md)，启动顺序原理见 [启动手册.md](启动手册.md)，踩坑速查见 [踩坑记录.md](踩坑记录.md)。

## 一、三种部署形态（先选型）

| 形态 | 适用场景 | 中间件 | 业务服务 | SRS | 文档章节 |
|---|---|---|---|---|---|
| **A. 本机开发** | 日常开发/调试（推荐） | Docker Compose | 原生 java -jar（按波次） | 原生 srs.exe | [§三](#三方案-a本机开发部署日常推荐) |
| **B. 一键脚本** | 本机快速拉起全套 | Docker Compose（脚本自动） | 脚本按波次拉起 | 手动 srs.exe | [§四](#四方案-b一键脚本) |
| **C. 全容器化** | Linux 服务器 / 演示交付 | Docker Compose | Docker 镜像 | SRS 容器（linux-full profile） | [§五](#五方案-c全容器化部署linux-服务器) |

**为什么 Windows 本机不用 SRS 容器**：Docker Desktop 的 UDP 端口转发丢包严重（WebRTC 握手超时），host 网络模式在 Windows 侧又不可达——所以本机用原生 `srs.exe` + `docker/srs-native.conf`（真实 UDP 套接字），SRS 容器只保留给 Linux（compose 里用 `profiles: linux-full` 隔离，`docker compose up` 默认不启动）。

## 二、环境前置条件

| 依赖 | 要求 | 说明 |
|---|---|---|
| JDK | 17（必须是 17） | 脚本默认找 `D:\enviroment\javaenviroment\jdk17`，不同路径设 `QIYU_JAVA_HOME` |
| Maven | 3.8+ | 全量构建用；jar 统一命名 `qiyu-live-xxx.jar`（finalName 已统一） |
| Docker Desktop | 运行中 | 中间件容器；Windows 上 Git Bash 需能调 docker 命令 |
| Node.js + pnpm/npm | 18+ | 前端 web_live / web_admin |
| ffmpeg | 在 PATH | 截帧巡查、视频转码、E2E 真实推流 |
| srs.exe | SRS 5 原生包 | 仅形态 A/B 需要；示例路径 `D:\softwarepackage\development\srs_v5\SRS\objs\srs.exe` |

可选环境变量（影响 start-all 脚本行为）：

```powershell
$env:JAVA_OPTS      = "-Xms128m -Xmx384m"   # 每个 JVM 的堆参数（14 个 JVM 共存，机器内存小就调小）
$env:QIYU_JAVA_HOME = "D:\enviroment\javaenviroment\jdk17"
$env:NACOS_ADDR     = "127.0.0.1:8848"
$env:STARTUP_WAIT   = 10                     # 每波次启动间隔秒数
```

## 三、方案 A：本机开发部署（日常推荐）

### 第 1 步：起中间件（Docker Compose）

```bash
set CANDIDATE=192.168.31.252
D:\softwarepackage\development\srs_v5\SRS\objs\srs.exe -c D:\桌面\project\qiyu-live-app\docker\srs-native.conf
```
```powershell
docker compose up -d        # docker-compose.yml：mysql/redis/nacos/rmqnamesrv/rmqbroker/minio
# SRS 容器默认不起（profiles 隔离）；停止: docker compose down
```

要点：
- **MySQL 首次启动自动执行 `sql/` 下全部建库建表脚本**（挂载到 `/docker-entrypoint-initdb.d`，只在数据目录为空时执行）；数据持久化在 `./docker-data/`；
- **RocketMQ broker 的 `brokerIP1 = 127.0.0.1`**（`docker/broker.conf`）——客户端必须拿到宿主机可达地址，改成容器内网 IP 会导致消费/生产连不上；
- 就绪判据：Nacos 控制台 `http://127.0.0.1:8848/nacos` 能登录（nacos/nacos）、MySQL `show databases` 列出 qiyu_live_* 各库、`http://127.0.0.1:39001` 打开 MinIO 控制台（minioadmin/minioadmin）。

### 第 2 步：初始化 Nacos 配置（全新环境一次）

服务启动时通过 `optional:nacos:qiyu-live-*.yaml` 导入配置，**全新 Nacos 必须先导入**：

1. 控制台 `http://127.0.0.1:8848/nacos`（nacos/nacos）→ 新建命名空间：ID 填 `ef63e53e-94c8-4b1c-865e-6824177b2893`，名称 `qiyu-live-test`（start-all 脚本也会自动建）；
2. 命名空间内 → 配置管理 → 配置列表 → **导入 `nacos-config/` 目录下的 `qiyu-live-*.yaml`**（dataId 与文件同名，group 为 DEFAULT_GROUP）；
3. 关键配置：`qiyu-live-user-shardingjdbc.yaml`（ShardingSphere 读写分离 + 100 分表，走 datasource-starter 的 Nacos SPI 扩展加载）、各服务的 Dubbo 端口/Redis/MySQL 连接。

### 第 3 步：构建

```bash
mvn clean install -DskipTests            # 全量；或 -T 1C 并行加速
mvn -pl qiyu-live-living-provider -am clean package -DskipTests   # 单模块增量（-am 必带）
```

> **旧 jar 陷阱**：jar 修改时间早于源码最后提交时间 = 旧包。启动脚本只在 jar 缺失时才自动构建，改过代码必须手动重新打包，否则"改了没生效"。

### 第 4 步：按波次启动 15 个 Java 服务

```powershell
# 等价于 scripts/start-all.ps1 start 的波次逻辑，手动版：
# Wave0 基础层（无 RPC 依赖，可并行）
java -jar qiyu-live-bank-provider\target\qiyu-live-bank-provider.jar
java -jar qiyu-live-account-provider\target\qiyu-live-account-provider.jar
java -jar qiyu-live-id-generate-provider\target\qiyu-live-id-generate-provider.jar
java -jar qiyu-live-im-provider\target\qiyu-live-im-provider.jar
# Wave1
java -jar qiyu-live-user-provider\target\qiyu-live-user-provider.jar
$env:DUBBO_IP_TO_REGISTRY="127.0.0.1"; $env:DUBBO_PORT_TO_REGISTRY="30035"
java -jar qiyu-live-im-core-server\target\qiyu-live-im-core-server.jar   # ⚠必须带这两个env
java -jar qiyu-live-gateway\target\qiyu-live-gateway.jar
java -jar qiyu-live-bank-api\target\qiyu-live-bank-api.jar
# Wave2 → im-router-provider / Wave3 → living-provider / Wave4 → msg,gift,video
# Wave5 → qiyu-live-api（最后）
```

两个硬性注意点：
- **im-core-server 必须注入 `DUBBO_IP_TO_REGISTRY` / `DUBBO_PORT_TO_REGISTRY`**：它把"自己的 ip:port"写进 Redis 供 im-router 定点寻址，不注入会在多网卡/localhost 场景注册错地址，弹幕收不到；
- **必须按依赖波次**：provider 类服务带启动自检（`QiyuProviderStartupVerifier`），上游没起会打印失败清单直接 `exit(1)`。依赖关系：im-router 依赖 im-core → living 依赖 im-router → msg/stream/gift 依赖 living+im-router → gift 还依赖 bank+user → api 最后。

### 第 5 步：启动 SRS（原生）

```bat
:: cmd，CANDIDATE 必须是本机局域网 IP（换机器必改，WebRTC candidate）
set CANDIDATE=192.168.31.252
D:\softwarepackage\development\srs_v5\SRS\objs\srs.exe -c D:\桌面\project\qiyu-live-app\docker\srs-native.conf
```

- hook 回调固定指向 `http://127.0.0.1:38090/api/stream/on_publish|on_unpublish|on_dvr`——**必须与 stream-provider 的 HTTP 端口一致**，不一致则开播状态/回放全部失灵；
- 改过 srs 配置要**重启 SRS 才生效**（踩过的坑）。

### 第 6 步：前端

```powershell
cd web_live;  npm run dev     # http://localhost:3000
cd web_admin; npm run dev     # http://localhost:3005（默认账号见 admin 建表脚本）
```

### 第 7 步：验证

1. 网关白名单接口：`http://127.0.0.1:38080/live/api/living/list` 返回 JSON（Nacos→gateway→api→living 全链路通）；
2. Nacos 服务列表 15 个服务各 ≥1 实例；`scripts\start-all.ps1 status` 全绿；
3. E2E 冒烟：`node scripts/e2e/e2e_test.mjs`（主链路），按需跑 `pay_ticket/dm/lottery/...` 各功能脚本，退出码 0 即通过。

## 四、方案 B：一键脚本

日常直接用（内部 = 方案 A 的自动化：端口探测跳过已起中间件、自动建 namespace、缺 jar 自动构建、按波次启动、pid 文件 + jps 双保险停止）：

```powershell
scripts\start-all.bat            # 全套（中间件 + 15 服务）
scripts\start-all.bat infra      # 只起中间件
scripts\start-all.bat build      # 只构建 mvn clean install -DskipTests
scripts\start-all.bat start      # 只启动服务（按 Wave0~5）
scripts\start-all.bat status     # 状态总览（中间件端口 + 各服务 pid）
scripts\start-all.bat logs qiyu-live-api   # 跟踪某服务日志
scripts\start-all.bat web        # 起 web_live vite dev（:3000）
scripts\start-all.bat stop       # 只停 Java 服务（jps 按 qiyu-live 匹配），不动中间件
scripts\start-all.bat restart
```

Linux/macOS/Git Bash：`bash scripts/start-all.sh`（逻辑与 ps1 一致）。脚本已知问题见 启动手册.md：stream-provider 在 Wave0 中但它依赖 living/im-router，自检 strict 环境建议把它移到 Wave4 之后。

## 五、方案 C：全容器化部署（Linux 服务器）

### 5.1 构建镜像

```bash
mvn clean install -DskipTests          # 先产出各模块 target/qiyu-live-xxx.jar
bash scripts/ops/build-images.sh           # 15 个服务 → qiyu-live/<模块名>:dev
# 原理：把 jar 拷到 docker/build/app.jar，用 docker/app.Dockerfile 打包
# app.Dockerfile = eclipse-temurin:17-jre + COPY app.jar
#   ENTRYPOINT: java -XX:MaxRAMPercentage=70 ${JAVA_OPTS} -jar /app/app.jar ${EXTRA_ARGS}
```

### 5.2 起全套

```bash
docker compose -f docker-compose-full.yml up -d
# Linux 需要流媒体时显式启动 SRS 容器：
docker compose -f docker-compose-full.yml --profile linux-full up -d srs
```

23 个服务一次拉齐：6 中间件 + 15 Java 服务 + web-front。**容器间不表达启动依赖**（depends_on 只指向中间件）——Nacos 模式下 Dubbo 引用是懒注册+运行期重试，靠重试兜底；手动起进程时才必须讲波次。

### 5.3 EXTRA_ARGS 覆盖机制（关键）

容器内服务通过 `EXTRA_ARGS` 环境变量以 Spring 启动参数覆盖 jar 内 bootstrap.yaml（**优先级最高**）：

```yaml
EXTRA_ARGS: >-
  --spring.cloud.nacos.config.server-addr=nacos:8848      # 容器网络内直连 nacos 容器名
  --spring.cloud.nacos.discovery.server-addr=nacos:8848
  --spring.cloud.nacos.discovery.namespace=ef63e53e-94c8-4b1c-865e-6824177b2893
  --dubbo.registry.address=nacos://nacos:8848?namespace=...&&username=nacos&&password=nacos
```

**换 Nacos 服务器 / 换 namespace 只改 compose 里的 EXTRA_ARGS，不用重打镜像**。数据源连接同样用 `SPRING_DATASOURCE_URL` 等标准环境变量注入。

### 5.4 宿主端口映射（compose-full）

| 端口 | 服务 | 用途 |
|---|---|---|
| 80 | web-front | 前端静态资源 |
| 38080 | gateway | 统一 HTTP 入口 |
| 38085 | qiyu-live-api | API（也可经 gateway 进） |
| 38095 | bank-api | 支付回调入口 |
| 38110 / 38115 | im-core-server | TCP / WebSocket 长连接 |
| 3306/6379/8848/9876/1935/1985/8080/8000/39000-1 | 中间件 | 按需映射 |

内部 Dubbo 端口（30010~30065）**不映射宿主机**，服务间走 docker 网络。

### 5.5 Linux 上的 SRS 容器

- 端口映射模式 RTMP/HTTP-FLV/HLS 均正常；**不能用 `network_mode: host`**（绑在 docker-desktop VM 内，外部不可达——Windows 上如此，Linux host 模式可用但与映射模式二选一）；
- `CANDIDATE` 环境变量必须改成服务器公网/局域网 IP，否则 WebRTC 握手超时；
- hook 回调地址写 `http://<stream-provider可达地址>:38090/api/stream/...`。

## 六、数据初始化与持久化

| 项 | 说明 |
|---|---|
| MySQL 建库建表 | `sql/` 目录挂载为 init 脚本，**仅首次**（数据目录为空）自动执行；之后新增的 sql（如 linkmic.sql、dm.sql）需手动执行 |
| 数据持久化 | 全部落在 `./docker-data/`（mysql/redis/nacos/srs/minio），`docker compose down` 不丢数据，`down -v` + 删目录才是重置 |
| MinIO 桶 | `qiyu-live-videos`（视频/封面/截帧）、DVR 录像；首次由服务自动创建（MinioConfig） |
| Nacos 配置 | §三 第 2 步；namespace `qiyu-live-test`（ID `ef63e53e-...`），数据持久化在 docker-data/nacos |
| RocketMQ Topic | `autoCreateTopicEnable = true`（broker.conf），发送时自动建 |

## 七、升级与回滚

1. **改代码后的标准升级流程**：`mvn package`（确认 jar 时间新于源码）→ 杀旧进程 → 起新 jar。只重启改动模块（`-pl <模块> -am`），不用全量重启；
2. **容器化升级**：改代码 → 重打镜像（`build-images.sh`）→ `docker compose -f docker-compose-full.yml up -d <服务名>` 单服务滚动重启；
3. **回滚**：镜像构建带 tag（`build-images.sh v1`）可回退旧 tag；jar 部署靠 git checkout + 重新打包；
4. **配置变更**：Nacos 控制台改完即发布（监听热生效为主，数据源/分片类配置需重启服务）。

## 八、部署常见坑速查（详见 踩坑记录.md）

| 坑 | 症状 | 解法 |
|---|---|---|
| brokerIP1 留容器内网 IP | MQ 收发全超时 | broker.conf 保持 `127.0.0.1`（本机）或宿主机 IP（服务器） |
| SRS CANDIDATE 不对 | WebRTC 握手超时 | 改为本机局域网/公网 IP 后重启 SRS |
| Windows 用 SRS 容器 | UDP 转发丢包、推拉流断 | 用原生 srs.exe + srs-native.conf |
| im-core 没带 DUBBO_IP_TO_REGISTRY | 弹幕收不到（Redis 绑定地址错） | 启动前注入两个环境变量 |
| 改码不重打包 | "改了没生效" | mvn package 后对比 jar 时间 vs 源码提交时间 |
| MySQL 新增 sql 未执行 | 新表缺失报错 | 首次初始化后才挂载的脚本要手动执行 |
| SRS hook 端口与 stream-provider 不一致 | 开播状态/回放失灵 | hook 指向 stream-provider HTTP 端口（当前 38090） |
| SRS 改配置没重启 | hooks 不生效 | 重启 SRS |
| 跨服务共享 Redis key 前缀错 | 数据"分裂"（PK 进度条写读不一致） | 共享 key 用固定常量前缀（PkConstants/TicketConstants） |
| 内存不足 | 14 个 JVM 启动慢/被杀 | `JAVA_OPTS=-Xms64m -Xmx256m` 或砍掉不需要的模块 |
| 旧 jar 静默运行 | 服务起来了但行为是旧的 | 见 troubleshooting §23；启动前核对 jar 时间 |
