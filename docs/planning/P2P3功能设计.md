## 一、总览与依赖关系

```text
P2-1 分成结算完整版（收益流水 + 抽成配置 + 提现审批）★地基，先行
  ├── P2-2 电商闭环 ── 其中的"带货分成"复用 P2-1 的流水表与抽成配置
  └── P2-3 大航海/贵族 ── 复用批次十五的粉丝团基建（FanConstants 亲密度），
                          大航海订阅扣费复用余额底座；贵族进场特效复用批次十五进场特效链路
P3-1 可观测性 ── 无依赖，可与 P2 并行（docker-compose 与 framework 改动为主）
P3-2 弹幕压测 ── 压测先行拿基线 → 降级预案按数据设计
P3-3 安全加固 ── 无依赖，可拆散做
P3-4 推荐系统 ── 依赖行为日志埋点（与 P3-1 的 metrics 埋点同期做）
```

建议排期顺序：**P2-1 → P2-2 → P2-3 →（穿插）P3-3 → P3-2 → P3-1 → P3-4**。
P2-1 是 P2 全线的地基（独立流水表），务必先行。

## 二、P2-1 分成结算完整版

### 2.1 现状与问题

| 现状 | 位置 | 问题 |
|---|---|---|
| 送礼分账 90% 直接入余额 | gift-provider `SendGiftConsumer` 内 `currencyAccountRpc.incr(receiverId, floor(price×0.9))` | 无独立流水，只有余额变动 trade 记录；抽成比例硬编码 `PROFIT_SHARE_RATIO=0.9` |
| 门票直接金币划转（观众 decr / 主播 incr） | api `LivingRoomServiceImpl.buyTicket` | 同上，且主播入账是 100%（无抽成） |
| 无提现 | — | 收益永远锁在虚拟余额里 |

### 2.2 设计

#### （1）收益流水表（qiyu_live_bank 库）

```sql
t_anchor_income_flow (
  id            bigint PK AUTO,
  anchor_id     bigint NOT NULL,
  biz_type      tinyint NOT NULL,   -- 1礼物分账 2门票 3带货分成(P2-2) 4提现冻结 5提现驳回退回 6手动调整
  biz_id        varchar(64),        -- 关联业务单号：送礼MQ流水id / 房间id / 订单id / 提现单id
  gross_amount  int NOT NULL,       -- 总收入（金币）
  platform_rate int NOT NULL,       -- 平台抽成千分比，如 100 = 10%
  net_amount    int NOT NULL,       -- 主播净入账 = gross - gross*rate/1000
  remark        varchar(200),
  create_time   datetime,
  KEY idx_anchor_time (anchor_id, create_time),
  KEY idx_biz (biz_type, biz_id)
)
```

- **写入点改造**：`SendGiftConsumer` 的 `incr(90%)` 与 `buyTicket` 的 `incr(100%)` 改为调 bank-provider 新 RPC
  `IIncomeRpc.recordIncome(anchorId, bizType, bizId, grossAmount)`，由 bank-provider 内部：
  ① 读平台抽成配置 → ② 写流水 → ③ `incr` 净额入余额（保持现有余额缓存/异步事务链路不变）。
- **可提现额口径**：`SUM(net_amount WHERE biz_type IN (1,2,3,5)) - SUM(gross_amount WHERE biz_type=4)`（一次 SQL）。
  不做第二个余额账户，**余额仍是唯一资金池**，流水是"收益账本"，防止双账户对不上的复杂度。

#### （2）平台抽成可配置

```sql
t_platform_config (
  conf_key   varchar(50) PK,      -- income.gift.rate / income.ticket.rate / income.shop.rate
  conf_value varchar(50),         -- 千分比字符串，如 "100"
  remark     varchar(200),
  update_time datetime
)
```

- bank-provider 读取：本地 Caffeine/Redis 缓存 60s，后台改配置后最迟 60s 生效（不做热推送，够用）。
- admin 端点：`/config/list`、`/config/update`（新 AdminConfigController）。
- 默认值：礼物 10%、门票 5%、带货 20%（种子 SQL）。

#### （3）提现申请 + 后台审批

```sql
t_withdraw_apply (
  id          bigint PK AUTO,
  apply_no    varchar(40) UNIQUE,   -- WD+yyyyMMdd+序列
  anchor_id   bigint NOT NULL,
  amount      int NOT NULL,         -- 提现金币
  status      tinyint NOT NULL,     -- 0待审 1已打款 2已驳回 3已取消
  reason      varchar(200),         -- 驳回原因
  operator    varchar(50),          -- 审批人
  apply_time  datetime, audit_time datetime,
  KEY idx_anchor (anchor_id, apply_time)
)
```

- **状态机**：`0待审 → 1已打款 / 2已驳回`；`0待审 → 3已取消`（主播自己撤回）。
- **资金动作**（关键设计决策）：
  - 申请时：校验可提现额 → 余额 `decr(amount)`（冻结语义）→ 写流水 `biz_type=4`（负向）；
  - 驳回时：余额 `incr(amount)` → 写流水 `biz_type=5`（退回）；
  - 打款时：仅改状态（mock 阶段无真实出金渠道，记 `operator` 留痕）。
  - 这样任意时刻"余额 + 在途提现 = 历史净收益合计"，对账自洽。
- **API**：
  - 主播侧（api 域）：`POST /bank/income/flow`（分页流水）、`GET /bank/income/summary`（可提现额）、`POST /bank/withdraw/apply`、`POST /bank/withdraw/cancel`
  - admin 侧：`/withdraw/list?status=`、`/withdraw/audit?id&pass&reason`
- **前端**：UserCenterPage 加"💰 收益"tab（可提现额 + 流水列表 + 提现按钮）；web_admin 加"提现审批"页 + "平台配置"页。

#### （4）工作量与验收

- 工作量：2~3 天（流水表改造 1 天、提现链路 1 天、前端两页 0.5~1 天）。
- 验收：送礼 100 金币（抽成 10%）→ 流水出现 gross=100/net=90 一条；申请提现 50 → 余额 -50 且可提现额随之减少；admin 驳回 → 余额 +50；对账 Job 把流水与 t_qiyu_currency_trade 抽样核对无差错。

## 三、P2-2 电商闭环

### 3.1 现状

`t_sku_order_info`（status：0待支付/1已支付/2已取消，无履约态）、`t_anchor_shop_info`（上架/下架，无审核）、订单支付后无主播分成、无评价。

### 3.2 设计

#### （1）订单履约物流状态机

在 `t_sku_order_info` 加列 `logistics_status`（与支付 status 解耦）：

```text
1待发货 → 2已发货 → 3已收货
                ↘ 4退款中 → 5已退款（观众侧申请，主播同意）
1待发货 → 5已退款（未发货直接退）
```

- 新表 `t_order_logistics(id, order_id UNIQUE, tracking_no varchar(64), operator varchar(50), update_time)` —— 模拟物流单号（mock 阶段主播手填或系统生成 `MOCK+序列`）。
- 每次流转写流水式日志 `t_order_log_flow(order_id, from_status, to_status, operator, remark, create_time)`（复盘争议用）。
- 广播：复用既有 bizCode **5562 订单状态变更**，下单/发货/收货/退款各节点推给买卖双方。
- API：主播 `POST /gift/order/deliver`（发货）、`POST /gift/order/refund/agree|reject`；观众 `POST /gift/order/confirm`（确认收货）、`POST /gift/order/refund/apply`。
- 前端：主播端 RoomPage"🛍 商品管理"弹窗内加"订单管理"页签（待发货列表/发货/退款处理）；UserCenterPage"我的订单"加状态列与"确认收货/申请退款"按钮。
- 定时兜底：发货 7 天未确认自动确认（复用延迟 MQ 模式，delayLevel=14×N 不够长 → 用 @Scheduled 每日扫表即可，量小）。

#### （2）商品审核

- `t_anchor_shop_info` 加列 `audit_status`：0无需(存量) 1待审 2通过 3驳回。
- 上架动作语义变更：`updateShopStatus(上架)` → 若未过审则置 `audit_status=1` 并进审核队列，**过审前不出现在小黄车**（gift-provider 查询加过滤 `audit_status=2`，存量数据 seed 时批量置 2）。
- 商品名/描述过一遍敏感词（复用 IRiskRpc.checkText，scene=6 商品）。
- admin：`/shop/auditList`、`/shop/audit`；web_admin 复用内容审核页模式新增"商品审核"页。

#### （3）带货分成（依赖 P2-1）

- 触发点：SKU 订单支付成功处（bank 侧 payNotify 对 SKU 订单的分支，或 gift-provider 现有 `SkuOrderMq` 消费点——以实际链路为准，消息体已有 `SkuOrderMqDTO`）。
- 逻辑：`IIncomeRpc.recordIncome(anchorId, bizType=3, orderId, totalPrice)`，抽成读 `income.shop.rate`（默认 20%）。
- 与履约解耦：支付成功即分成（简化）；若后续要做"退款追回分成"，在 5已退款 时写一条负向流水（biz_type=6 手动调整，remark 关联订单），表结构已支持。

#### （4）SKU 评价体系

```sql
t_sku_order_comment (
  id bigint PK AUTO,
  order_id bigint UNIQUE,       -- 一单一评
  sku_id bigint, user_id bigint, anchor_id bigint,
  rating tinyint,               -- 1~5 星
  content varchar(300),
  create_time datetime
)
```

- 仅 `logistics_status=3已收货` 可评；内容过敏感词（scene=4 评论）。
- 查询：小黄车商品卡/详情显示"评分 n.n（m 条）"（AVG 聚合，Redis 缓存 5min）。
- 前端：我的订单"评价"按钮弹窗（星级 + 文本）；商品卡悬停显示评分。

#### （5）工作量与验收

- 工作量：3~4 天（状态机+广播 1 天、审核 0.5 天、分成 0.5 天、评价 1 天、前端 1 天）。
- 验收：下单支付 → 主播收到 5562 → 发货 → 观众确认收货 → 评价 5 星 → 主播收益流水出现带货分成一条；退款链路走通并验证分成不重复入账。

## 四、P2-3 大航海 / 贵族体系

### 4.1 依赖

批次十五粉丝团基建：`FanConstants.FAN_POINTS_KEY_PREFIX`（亲密度 hash）、进场特效（RoomPage `entrance-effect` 组件分级动画）、`MessageDTO.fanLevel`。

### 4.2 大航海（月度订阅，对标 B 站舰队）

```sql
t_guard_sub (                                    -- user 库
  id bigint PK AUTO,
  user_id bigint, anchor_id bigint,
  tier tinyint,                                  -- 1舰长 2提督 3总督
  price int,                                     -- 月费金币：198 / 1000 / 20000
  start_time datetime, expire_time datetime,
  status tinyint,                                -- 1生效 0过期
  UNIQUE uk_user_anchor(user_id, anchor_id)      -- 一人对一主播同时仅一档
)
```

- **购买**：api `POST /guard/subscribe`（anchorId, tier）→ 余额 decr → user-provider upsert（续费=expire_time+30d）→ 写 MQ 广播全房间 **5578 开通/续费大航海**（"xxx 开通了总督！"全屏特效，复用 entrance-effect）→ 亲密度一次性 +price（复用 FanConstants，直接顶到高灯牌）。
- **到期**：延迟 MQ（30d 超出 RocketMQ 最大档 → 用 @Scheduled 每日扫 `expire_time < now` 置过期，量小）+ 过期前 3 天进房时系统提示续费。
- **权益落地**：
  - 勋章：`MessageDTO +guardTier`；msg-provider 弹幕链路查 user-provider 新 RPC `getGuardTier(roomAnchorId, userId)`（user 库直查，Redis 缓存 5min key `qiyu:live:guard:{anchorId}:{userId}`）；ChatList 渲染"舰/督/总"色块（蓝/紫/金）。
  - 进场特效：欢迎广播带 guardTier，RoomPage effect 分级（舰长=灯牌 L4 同级，总督 > 灯牌 L5）。
  - 优先发言：v1 仅 UI 徽章排序（ChatList 中带舰队标识的消息不参与抽样丢弃，见 P3-2 降级预案联动）。

### 4.3 贵族（个人身份，对标斗鱼/虎牙，跨直播间生效）

```sql
t_noble ( user_id bigint PK, level tinyint,   -- 1骑士 2伯爵 3公爵 4国王
          expire_time datetime )
```

- 购买：任意页面头像菜单"👑 贵族"入口，月费（99/299/999/2999），余额扣款，跨直播间生效。
- 进场座驾特效：复用欢迎广播链路，`MessageDTO +nobleLevel`；lottie 素材位（`web_live/src/assets/lottie/` 放 noble-1~4.json，进场特效组件按 nobleLevel 优先播放 lottie，无素材时退化为 CSS 动画）。
- **徽章优先级**：贵族 > 大航海 > 灯牌 > 用户等级（ChatList 渲染顺序，避免堆叠）。

### 4.4 admin 与验收

- admin 配置页：舰队档位价格、贵族档位价格（t_platform_config 扩 key）。
- 验收：A 订阅 B 舰长 → 余额 -198、B 看到全屏特效、A 弹幕带舰长徽章、亲密度 +198；到期次日徽章消失。

### 4.5 工作量

- 大航海 1.5 天 + 贵族 1.5 天（含特效素材位与 admin 配置）；lottie 素材本身用占位 JSON。

## 五、P3-1 可观测性

### 5.1 Metrics（第一步，1 天）

- framework `web-starter` 统一加 `spring-boot-starter-actuator` + `micrometer-registry-prometheus`，全部服务暴露 `/actuator/prometheus`（网关放行该路径仅限内网）。
- 手动业务埋点（Micrometer Gauge/Counter）：
  - `im_online_connections`：im-core-server 在线 Channel 数（最核心业务指标，Netty ChannelGroup size）
  - `qiyu_danmu_total{room}`：弹幕吞吐 Counter
  - `qiyu_balance_op_total{op=incr|decr}`：资金操作计数（对账联动）
  - Dubbo QPS/RT、JVM：框架自带
- docker-compose-full.yml 加 `prometheus` + `grafana` 两服务，预置 dashboard JSON 四块：JVM / Dubbo / IM 连接数 / 业务指标。

### 5.2 告警（第二步，0.5 天）

- Alertmanager → 飞书/钉钉机器人 webhook。规则：服务实例 down、MQ 堆积 > 1w、支付回调失败连发、对账差错表新增（`t_reconciliation_detail` 当日 count > 0）、CPU/内存阈值。

### 5.3 链路追踪（第三步，1 天）

- SkyWalking agent：`docker/app.Dockerfile` ENTRYPOINT 支持 `SW_AGENT_OPTS` 附加 `-javaagent:/sw/skywalking-agent.jar`；本机 jar 模式在 start-all.sh JAVA_OPTS 加同参数（可开关）。
- 覆盖 HTTP 网关 → Dubbo → RocketMQ 全链路；现有彩色日志保留，logback pattern 加 `%tid`（SkyWalking 提供 MDC 值）实现日志-Trace 串联。

### 5.4 日志聚合（第四步，0.5~1 天）

- 选型 **Loki + Promtail**（比 ELK 轻一个量级，与 Grafana 同栈）：Promtail 采集 `logs/*.log`，Grafana 内 Logpanel 按 traceId/服务检索。
- 验收：Grafana 从一张告警点进对应 trace，再从 trace 跳到 Loki 日志行。

## 六、P3-2 弹幕压测与热房降级

### 6.1 压测（先行，1 天）

- `scripts/im_benchmark.mjs`（Node ws 客户端，参考现有脚本握手协议）：梯度 1k → 5k → 1w 连接，同一批连接进同一"压测房间"。
- 采集指标：连接建立成功率、1001 登录 RT P50/P99、5555 广播端到端 RT（发送者打时间戳，接收端回报）、5s 丢消息率。
- 产出 `docs/ops/容量基线.md`：单机 im-core 在 1w 连接 / 单房间 1w 观众下的广播 RT 基线数据。
- 注意：压测会污染 Redis 房间 Set 与等级/亲密度 key，压测专用 appId（新增 AppIdEnum.PRESSURE=19999）或压测前缀 userId，跑完全量清理。

### 6.2 热房降级预案（按基线数据决定做不做、做多少）

已知瓶颈：`SingleMessageHandlerImpl` 每条弹幕 `livingRoomRpc.queryUserIdByRoomId` → im-router 对房间 Set 全量 SCAN/拉取，广播 O(n) 组包。

三级预案（按需启用，配置开关 `qiyu.danmu.hot-mode-threshold`）：

1. **抽样广播**：房间在线 > 500 时，普通弹幕 5555 按 `min(1, 500/n)` 比例抽样下发（系统消息 5556/5563/5566/5574/5576 全量）；发送者本人始终全量回显。
2. **房间广播通道**：im-router 不再按 userId 组包逐推，改为"房间号 → im-core 广播"（im-core 内维护 room→channels 注册表，进房/心跳/登出维护，广播一次扇出）；msg-provider 只发一条 `roomId` 消息。
3. **前端合帧渲染**：ChatList 用 requestAnimationFrame 批量 flush（每帧上限 50 条，超出丢中间普通弹幕），弹幕降频不降序。

### 6.3 工作量

压测 1 天；预案 1（0.5 天）、预案 2（2 天，动 im-core/im-router 核心，需评审）、预案 3（0.5 天，纯前端）。**建议做完压测拿到数据后再决定 2 是否实施。**

## 八、P3-4 推荐系统（分两阶段）

### 8.1 阶段一（1 天）：规则 + 标签召回

- 行为埋点：`t_user_action_log(user_id, video_id, action[曝光/点击/播放/完播/点赞/评论/分享], weight, create_time)`，video 播放/点赞等现有点位异步写 MQ（复用 `USER_EXP_CHANGE_TOPIC` 模式，新 Topic `VIDEO_ACTION_TOPIC`）。
- 用户偏好表：`t_user_tag_weight(user_id, tag_id, weight)`，消费端滚动累加（衰减因子 0.95/天，@Scheduled 每日重算）。
- feed 排序升级：现热度分 `play*0.4+like*0.3` → `热度 × (1 + 用户该标签偏好权重)`，同池去重不变。
- 效果指标：分桶（userId%100）对比人均完播率/点赞率，写回 backlog。
